# code-reviewer — baseline iter2 (2026-07-02)

Follow-up to iter1, adding **two subtler fixtures** to test whether the skill improves
*detection* (not just severity discipline) on bugs a strong model might wave through:

- `dual-write-no-outbox` — a DB update + a separate queue publish, no transaction/outbox
  (fails **only** under partial failure; the happy path looks correct).
- `money-as-float` — currency math in IEEE-754 floats (passes round-number tests; drifts on
  real inputs like `1.005 * 100`).

Same method as iter1: with-skill vs baseline (plain "senior engineer, review this") on the
**same underlying model** (Opus 4.8, inherited), author-graded against `evals.json`,
**single run per config**.

## Result

| Config | Subtle cases (5–6) |
|---|---|
| **with-skill** | **8 / 8 (100%)** |
| **baseline** | **6 / 8 (75%)** |

**The detection-delta hypothesis did not hold.** The baseline caught the substance of
**both** subtle bugs:

- dual-write (baseline, quoted): *"the DB update and the event publish are two independent
  awaits with no transaction or outbox … if publishJSON throws (or the process dies between
  the two calls) … downstream consumers silently never run. This is the core correctness
  bug."* → recommended a transactional outbox.
- money-as-float (baseline, quoted): *"`1.005 * 100 = 100.49999999999999` → rounds to `100`,
  not `101` … For money, use integer cents throughout or a decimal library."*

The entire +25pp delta is, once again, **severity-vocabulary discipline**: the with-skill
runs labeled both **BLOCKER**; the baseline said *"Request changes" / "core correctness
bug"* with no BLOCKER/HIGH label (expectation 4 miss in each case).

## Combined (iter1 + iter2), discriminating cases 1–3 + 5–6

| Config | Expectations | Pass rate |
|---|---|---|
| with-skill | 21 / 21 | **100%** |
| baseline | 17 / 21 | **81%** |

Plus the over-trigger control (case 4): with-skill passes (declines + routes).

## Interpretation — what the skill is actually for

On a **frontier model, this skill does not catch more bugs** than a plain review — it
**standardizes** them: an enforced `BLOCKER/HIGH/MEDIUM/LOW/QUESTION` contract, a
structured findings/verdict output, explicit archetype/lens framing, and a clean
over-trigger boundary. Its ROI is **consistency and reviewability**, not detection.

Where the skill likely *does* move detection (not tested here, worth a future iter):
- weaker/cheaper models, where the lens checklist and scripts backstop gaps;
- very large diffs that exceed a single context, where `list-review-surface.sh` +
  subagent routing keep coverage from degrading;
- teams wanting *uniform* severity/format across many reviewers.
